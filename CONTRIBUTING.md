# Contributing to DemoTape

Thanks for taking the time to contribute. This document covers how to report bugs, propose
features, and submit pull requests — including PRs generated by a coding agent (Claude Code,
Codex, Kiro, etc.), which is a normal and welcome way to contribute here.

If you're an AI agent picking up this repo to make a change, read [`AGENTS.md`](AGENTS.md) first
— it has the build/test commands, the hard technical constraints, and troubleshooting. This file
is about process and review standards; `AGENTS.md` is about how to actually build and verify.

## Before you start

- **Search existing issues and PRs first** — someone may already be working on it, or it may
  already be on the [roadmap](README.md#where-it-could-go) or explicitly marked
  [Planned](README.md#planned) (not yet implemented, don't expect it to work).
- **For anything non-trivial, open an issue before opening a PR.** A quick description of the
  problem and proposed approach saves everyone a rewritten PR later. Small fixes (typos, obvious
  bugs, doc corrections) can go straight to a PR.
- **Security issues do not go here.** Follow [`SECURITY.md`](SECURITY.md) — private reporting
  only, never a public issue or PR.

## Reporting bugs / requesting features

Open a GitHub issue with:

- A reproducible test case or clear steps
- The DemoTape version (About menu, or git tag/commit) and macOS version
- What you expected vs. what happened
- Anything unusual about your setup (Intel vs. Apple Silicon, local AI vs. hosted keys, etc.)

## Hard constraints (non-negotiable)

These come from `AGENTS.md` and apply to every PR, human- or agent-authored. A PR that violates
one of these will be asked to change, regardless of how well-tested it otherwise is:

- **Target macOS 12.3+.** No API newer than macOS 13 without an `@available` guard.
  `ScreenCaptureKit` is intentionally avoided (see `AGENTS.md` for why) — capture stays on
  `AVCaptureScreenInput`.
- **No third-party dependencies.** Apple frameworks only. This is a design goal, not an
  oversight — don't add a package to solve something Apple's frameworks already do.
- **Local by default.** The core recorder/render/publish path makes no network calls. Network
  access is only allowed in explicitly opt-in AI features, and only to the endpoint the user
  configured.
- **Keys go in the Keychain**, never `UserDefaults`, never committed, never logged.
- **Don't commit build artifacts** — recordings, `.app` bundles, `.build/`, signing identities.
  Check `.gitignore` covers what you're adding.

If your change needs an exception to one of these (e.g. a new API that genuinely requires macOS
13+), say so explicitly in the PR description and why there's no 12.3-compatible path — don't
just add the guard and hope it's not noticed.

## Making a change

```bash
swift build -c release   # must succeed
swift test                # 422+ tests: pure logic only, no GUI, no network — all must pass
```

For anything touching rendering, encoding, captions, or publish, also exercise the relevant
headless hook from `AGENTS.md` (`--render`, `--transcode`, `--captions`, `--publish`, `--frame`,
etc.) and actually look at the output — a still frame or exported clip, not just a log line
saying it ran.

Guidelines:

- **Keep it scoped.** One PR, one concern. Don't bundle a refactor with a feature with a typo
  fix — it makes review slower and revert riskier.
- **Match existing style.** Look at the surrounding file before introducing a new pattern.
- **Add or extend tests for new pure logic** (parsing, formatting, URL/endpoint building). Keep
  tests network-free — factor testable logic out of the network call itself, the way
  `Captions.parseCues` / `transcriptionEndpoint` already do.
- **No drive-by cleanup.** If you spot an unrelated issue while working, file a separate issue
  or PR for it instead of folding it in.

## Pull requests generated by a coding agent

Agent-authored PRs are welcome and reviewed the same way as human ones — the standards above
apply in full, not as a lighter "best effort" version. A few things that specifically matter for
agent output:

- **The PR description must state what was actually run**, not just what was intended: which of
  `swift build -c release`, `swift test`, and any headless hooks were executed, and their result.
  "Should work" is not a substitute for a build/test log.
- **No invented dependencies or APIs.** Agents sometimes reach for a package or a newer API
  because it's the common pattern elsewhere — that's exactly what the hard constraints above
  forbid here. If the agent added an import that isn't Apple-framework-only, that's an automatic
  request for changes.
- **Verify claims against real output.** If the PR says "captions are burned in correctly" or
  "the zoom now frames the button," that should be backed by an actual frame grab
  (`--frame`) or exported clip attached or described in the PR, not just asserted. This project's
  whole verification philosophy (see `README.md#verified-demos-one-use-case`) is that a claim
  needs evidence — hold agent PRs to the same bar the tool itself enforces on demos.
- **Small, reviewable diffs.** An agent can produce a large diff quickly; that doesn't make it
  right-sized for review. If a task naturally splits into independent pieces, prefer several
  small PRs over one large one.
- **For anything visual, attach a short video or GIF of the result (optional but encouraged).**
  If your change touches recording, rendering, captions, voiceover, zoom/cursor behavior, or any
  UI, a 10-30 second clip showing before/after is worth more than a description. Fitting, since
  this is DemoTape: use the app on itself — record the change, or generate a demo with the
  `demo-driver` skill (see `README.md#5-let-your-agent-record-a-verified-demo`). A GIF works fine
  for something short; a full recording works for a multi-step flow. Not required for non-visual
  changes (pure logic, parsing, config) — a passing test or a `--frame` grab covers those.

  **How to attach it:** drag the file into the PR comment box (or the attach-file icon in the
  formatting toolbar) — do **not** commit video files to the repo. GitHub uploads it to its own
  asset storage and drops in a link; nothing lands in git history or counts toward repo size.

  **Size limits (GitHub-enforced):** `.mp4`/`.mov`/`.webm` videos are capped at **10MB on GitHub
  free plans** and **100MB on paid plans**; GIFs and images at 10MB. If a raw clip doesn't fit,
  don't fight it — use DemoTape's own export path to get under the limit instead of trimming
  quality blindly:
  - `--publish styled.mp4 360` — web tier + a `demo.gif` in one step, sized for exactly this
  - `--transcode styled.mp4 360 out.mp4` — just the small MP4 tier
  - A 10-15s GIF of the specific change is usually more useful for review than a long MP4 anyway
    — trim to the part that actually demonstrates the fix.
- **Disclose agent involvement in the PR description** (e.g. "drafted with Claude Code, reviewed
  and tested locally by @you"). This isn't a mark against the PR — it just tells reviewers what
  level of scrutiny to apply and helps us track how agent-assisted contributions are going.

## Commit messages and PR description

- Commit messages: short imperative summary line, body if the "why" isn't obvious from the
  diff.
- PR description should cover: what changed, why, what was run to verify it (see above), and
  any deliberate deviation from the hard constraints.
- Reference the related issue if there is one (`Fixes #123`).

## Changelog

If your change is user-visible (a feature, a behavior change, a fix someone would notice, a
removed option), add a line under the `## [Unreleased]` heading in [`CHANGELOG.md`](CHANGELOG.md),
in the right group (Added / Changed / Fixed / Removed). Purely internal changes (refactors, test-only
edits, CI) don't need an entry. Maintainers move the Unreleased entries under a version heading at
release time — the per-release history there is generated from GitHub Releases, which stays the
source for downloadable DMGs and checksums.

## Review process

- A maintainer will review for: correctness, alignment with the hard constraints above, test
  coverage for new logic, and whether the change fits DemoTape's local-first, dependency-free
  design goal.
- Expect requests for changes rather than a straight merge on anything non-trivial — that's
  normal, not a sign the PR was unwelcome.
- Once approved, a maintainer will merge. Please don't merge your own PR unless explicitly asked
  to.
